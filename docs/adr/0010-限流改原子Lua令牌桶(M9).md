# ADR 0010:限流改原子 Lua 令牌桶(M9)— 移除 Bucket4j、搶購三層合併為單一腳本

日期:2026-09-25|狀態:已採納(M9 實作中)

## 背景

ADR 0008 §10 認定壓測長尾延遲的根因是 `seckill:rl:global` 熱 key 排隊,當時只坐實根因、未修限流器。
之後在 OCI 上分階段量測(計畫 [`docs/plans/2026-09-15-oci-load-test-stages.md`](../plans/2026-09-15-oci-load-test-stages.md),
數據在 [`docs/load-test-report.md`](../load-test-report.md) §14.4–14.7):

- **階段 3**:Bucket4j 的樂觀 CAS(GET → Java 端計算 → EVAL 比對寫回)在同一把 key 上,同一版本只能有一個 CAS 成功,
  其餘全部重試。單 key 安全在途數約 10、絕對上限約 6,200 次/秒(在途 1),而且 Redis 與 client 的 CPU 都沒滿,
  換大節點無效。
- **階段 4**:依此算出 sharded counter 最少 2 片、建議 4 片。
- **階段 5**:改用單一原子 Lua 腳本(讀、算、寫在 Redis 內一次完成),一把 key 放行精準 3000/s,
  在途 200 時 p99 5.0ms,沒有拐點、零重試,總檢查上限約 8.5 萬次/秒(Redis 單執行緒約 94%)。

**本里程碑的範圍**(使用者 2026-09-25 拍板):以原子 Lua 令牌桶取代 Bucket4j,**四層限流全部換掉**;
搶購路徑的三層(全域 / 單 IP / 單用戶)合併成一支腳本。

**不含**:設計文件 Phase 2 的「Rate Limiter as a Service」(獨立服務 + SDK),見 §1 取捨。

---

## 1. 以專案內的 Lua 令牌桶取代 Bucket4j(偏離設計文件 MVP 選型)

- **決策**:四層限流(global / ip / user / token_user)全部改走專案內的 Lua 腳本,移除 `bucket4j_jdk17-core`、
  `bucket4j_jdk17-lettuce` 兩個依賴與 `RateLimitConfig` 的專用 Lettuce 連線。**本節取代 ADR 0004 §4 的「後端:Bucket4j + Lettuce `ProxyManager`」**;
  同節的取 IP 方式(已由 ADR 0008 取代)不受影響。
- **理由**:Bucket4j 的 Lettuce 整合只有 CAS 一種模式,熱 key 下的重試風暴是它的本性(階段 3),不是設定能調掉的。
  Lua 版在同一台主機、同一套量法下上限是 CAS 的 13.6 倍,且放行量不會因競爭掉到設定值以下(報告 §14.7)。
  另外專案 CLAUDE.md 要求「Redis 多步驟臨界區一律 Lua」,扣庫存與 token 校驗早已是 Lua,限流是唯一的例外。
- **取捨**:
  - **偏離設計文件**:設計文件第 1、2、10 節寫的是「MVP 先用 Bucket4j + Redis 頂替,Phase 2 換自研 Rate Limiter」。
    本決策是把「換掉 Bucket4j」提前做,但只做演算法層的替換,**不做** Phase 2 的獨立服務與 SDK。
    Phase 2 仍可在日後把這支腳本搬進獨立服務。設計文件的對應段落要同步改寫(待使用者確認)。
  - 令牌桶演算法從「交給函式庫」變成「自己維護」:補充計算、時間來源、TTL 都要自己寫測試。
    腳本約 40 行,已在階段 5 驗過放行精準度。

## 2. 不做 sharded counter(推翻計畫 §5.3 的建議 4 片)

- **決策**:全域限流維持**一把 key**,不拆片。
- **理由**:分片解決的是「同一把 key 上的 CAS 重試」,原子腳本沒有重試,問題本身消失了。
  以計畫 §5.1 的公式回推:3000/s × 單次耗時要超過 67ms,在途數才會超過量到的 200,
  而量測範圍內 p99 最高約 5ms。
- **取捨**:一把 key 的上限最終還是 Redis 單執行緒(約 8.5 萬次檢查/秒,且那是這支腳本獨佔 Redis 時的數字)。
  若日後流量逼近,再拆片或拆 Redis 節點;腳本已按「一把 key 一個桶」寫,拆片時不用改演算法。

## 3. 搶購路徑三層合併成一支腳本,全有或全無扣 token(使用者可見的行為改變)

- **決策**:`/seckill/purchase` 的全域、單 IP、單用戶三層改由**一支腳本**一次檢查:先算出三個桶補充後的 token 數,
  **三層都至少有 1 個 token 才同時各扣 1**;任何一層不足就三層都不扣,並回傳是哪一層擋下。
  未登入(`userId == null`)時只傳全域與 IP 兩把 key。`/seckill/token` 的 token_user 維持單層、同一支腳本傳一把 key。
- **理由**:現行 `SeckillRateLimitInterceptor` 依 global → ip → user 順序逐層 `tryConsume`,**每一層檢查時就扣掉 token**,
  `&&` 短路只保證「前層擋下則不扣後層」。反過來,被 ip 或 user 層擋下的請求**已經扣掉了一個全域 token**。
  一個人狂刷時,他每一個被單用戶限流擋下的請求都在消耗全站 3000/s 的額度;極端情況下少數人就能把全域額度吃光,
  讓其他人全部拿到 429。單用戶與單 IP 限流本來就是要擋這種人,但它們排在全域之後,擋不住對全域額度的消耗。
  全有或全無修掉這件事;順帶把一次搶購的限流 Redis 往返從約 5 趟(Bucket4j 每層 GET + EVAL)降為 1 趟。
- **取捨**:
  - **行為改變**:被拒絕的請求不再消耗任何一層的額度。對正常使用者是更公平;對「靠大量請求擠掉別人」的人是變嚴。
    回應碼與訊息不變(仍是 3004 / HTTP 429),前端不需改。
  - 一支腳本碰 2–3 把 key。現行是單一 Redis,沒有問題;日後改 Redis Cluster 時,這幾把 key 要用 hash tag 落在同一個 slot,
    但 global 是全站共用、user/ip 是分散的,**天生無法同 slot** —— 屆時必須拆回多次呼叫,並重新處理全有或全無(例如先查後扣的補償)。
    列為已知限制。
  - 階段 5 量的是單 key 腳本;合併版每次讀寫 2–3 把 key,單次成本會高一些,**未量**。實作後以 bench 補量(§9)。

## 4. 腳本語意:Redis TIME、整數微 token、以補滿時間為 TTL

- **決策**:沿用階段 5 驗過的單 key 腳本語意(`load-test/ratelimit-bench/src/main/resources/token_bucket.lua`):
  - 時間取 Redis `TIME`,不收 client 時間
  - 每個桶是一個 hash:`t` = 剩餘微 token(token × 10⁶,整數)、`ts` = 上次更新的 Redis 時間(微秒)
  - 補充 = 經過微秒 × 每秒容量,上限為容量;key 不存在視為滿桶
  - TTL = 空桶補滿所需時間 + 1 秒;容量即每秒速率,補滿恆為 1 秒,所以實際固定 2 秒
  - **被擋下時不寫回**:狀態是「上次更新的 token 數 + 時間」,不寫回時下次讀取照樣從舊時間補充到現在,結果相同。
    代價是拒絕只有讀、沒有寫,比放行便宜(與階段 5 bench 的單 key 腳本不同,那一版拒絕也寫回)
  - 容量語意與現行 `RateLimiterService.perSecond()` 一致:容量 N、每秒平滑補滿 N、初始為滿
- **理由**:多個 backend 實例共用同一把全域 key,用 client 時間會讓各機時鐘漂移直接變成限流誤差。
  整數微 token 讓補充量恰為整數,不會累積浮點誤差。過期即滿桶,與不過期時的計算結果相同,所以 TTL 只影響記憶體、不影響語意。
- **取捨**:每次檢查多一次 `TIME` 呼叫(Redis 端微秒級)。Redis 7 的腳本一律以效果複寫,腳本內呼叫 `TIME` 不影響複寫一致性;
  **若日後降回 Redis 5 以下需重新檢視**(本專案鎖 Redis 7)。

## 5. key 改用新前綴 `seckill:ratelimit:*`,不沿用 `seckill:rl:*`

- **決策**:`seckill:ratelimit:global`、`seckill:ratelimit:ip:{ip}`、`seckill:ratelimit:user:{userId}`、`seckill:ratelimit:token:user:{userId}`。
- **理由**:Bucket4j 在 `seckill:rl:*` 存的是**字串**型別的序列化桶,新腳本用 **hash**。沿用同名 key,部署當下舊 key 還在
  (TTL 最長約 10 秒),新腳本 `HMGET` 一個字串 key 會得到 `WRONGTYPE`,請求直接 500。
  換前綴讓新舊 key 互不相干,舊 key 自然過期即可,不需要部署時手動清 Redis。
- **取捨**:部署切換的那一刻,新桶都是滿的,等於限流狀態重置一次(最多多放行一個容量的量,全域為 3000 個)。
  與現行重啟 backend 時的行為相同(Bucket4j 桶在 Redis,重啟不重置,但換 key 等同重置),可接受。

## 6. 保留一條限流專用的長駐 Lettuce 連線,不走 `StringRedisTemplate`

> 2026-09-25 實作時修訂:草稿原寫「走 `StringRedisTemplate`、刪除 `RateLimitConfig`」,實測後推翻,理由見下。

- **決策**:`RateLimitConfig` 保留,改為建一條 `StatefulRedisConnection<String, String>`(原本是 Bucket4j 需要的 `String/byte[]` codec)。
  `RateLimiterService` 直接用 Lettuce `EVALSHA` 送腳本,收到 NOSCRIPT(Redis 重啟清空腳本快取)時改送一次完整 `EVAL`。
- **理由**:[`RedisConfig`](../../backend/src/main/java/com/seckill/config/RedisConfig.java) 為了壓測調優關閉了 `shareNativeConnection`,
  但 `spring.data.redis.lettuce.pool.enabled` 沒有設,程式碼只在明確為 `true` 時才建連線池。結果是
  **每次 `StringRedisTemplate` 呼叫都新開一條 TCP 連線**:Testcontainers 實測 200 次限流呼叫,Redis `total_connections_received` 增加 201。
  限流在每個搶購請求的最前緣,3000/s 就是每秒 3000 次 TCP 建立 + AUTH,而且與階段 5 量測的「單一共享連線」形狀完全不同,
  量到的數字就不能沿用。專用長駐連線讓正式路徑與 bench 一致,也與 Bucket4j 時代的連線形狀相同(ADR 0004 §4)。
- **取捨**:專案裡執行 Lua 有兩種寫法(限流走 Lettuce 原生、扣庫存與 token 校驗走 template)。
  `RateLimiterServiceIT.checksReuseOneConnection` 釘住「限流不新開連線」,防止日後有人為了統一寫法改回 template。
  **template 每次新開連線這件事本身影響扣庫存、token 校驗等所有 Redis 路徑**,不在本 ADR 範圍,另列為待辦(見已知限制)。

## 7. Redis 失敗時的行為維持現狀:例外往上拋

- **決策**:腳本呼叫失敗(Redis 斷線、逾時)不在限流層吞掉,例外交給全域處理器,與現行 Bucket4j 版相同。
- **理由**:CLAUDE.md 禁止吞例外;fail-open(Redis 掛了就全部放行)會在最需要保護的時候把流量全部放進下游,
  而下游的扣庫存同樣依賴 Redis,放行也只是換個地方失敗。
- **取捨**:Redis 短暫不可用時搶購端點回 5xx 而不是 429,與現況相同,不是新引入的行為。

## 8. 指標:check.duration 的 layer 改為呼叫點,被拒絕時記錄是哪一層

- **決策**:
  - `seckill.ratelimit.check.duration` 的 `layer` 標籤由 `global / user / ip / token_user` 改為 `purchase / token_user`
    (一次呼叫就是一次檢查,無法再分層計時)。
  - 被限流時 `seckill.requests{result=rate_limited}` 之外,新增 `seckill.ratelimit.rejected{layer=global|ip|user|token_user}`,
    由腳本回傳的擋下層決定。
- **理由**:合併後只剩一次 Redis 呼叫,分層計時沒有意義;但「是哪一層在擋人」是調門檻時最需要的資訊,
  現行版本其實拿不到(只有總數),這次順手補上。
- **取捨**:`layer=global` 的時間序列會斷掉。已查 `infra/` 下沒有任何 Grafana 面板或告警規則引用這個指標,
  使用者只有壓測時的手動查詢(計畫 §1.5 以 `sum by (le, layer)` 分層看 p99),日後改看 `layer="purchase"`。

## 9. 驗收:Testcontainers 併發測試 + bench 補量合併腳本

- **決策**:
  - 改寫 `RateLimiterServiceIT`:各層容量上限、補充速率、**被 user 層擋下時 global 與 ip 的 token 不減少**(§3 的核心)、
    未登入只查兩層、新舊前綴不衝突(預先放一個字串型別的 `seckill:rl:global` 不影響新 key)。
  - 新增多執行緒併發測試:N 條執行緒同時打全域層,放行數不超過容量(不超放),且不因競爭少於容量(不少放)。
  - `ratelimit-bench` 新增合併腳本模式,在 OCI 拋棄式 Redis 上補量 3 把 key 版本的上限,結果補進報告 §14.8。
- **理由**:§3 的全有或全無是這次唯一的行為改變,必須有測試直接證明;bench 補量回答 §3 取捨裡「未量」的那一項。
- **取捨**:bench 補量要再上一次 OCI(拋棄式 Redis,不碰正式流量),約 10 分鐘。

## 影響

- **設計文件**:第 1 節(Phase 2 說明)、第 2 節架構圖與請求流程、第 3 節選型表、第 10 節、第 15 節 Phase 2 共 6 處改寫為 Lua 令牌桶,
  並註明 Phase 2 獨立服務仍保留;第 6 節 Redis 資料結構表補上限流 key。使用者 2026-09-25 確認(連同 §3 行為改變與 Cluster 限制)。
- **設定**:`seckill.ratelimit.*` 四個容量與 bypass 開關的名稱、預設值、環境變數**全部不變**,正式站 `.env` 不用動。
- **依賴**:移除 `bucket4j_jdk17-core`、`bucket4j_jdk17-lettuce` 與 `bucket4j.version` 屬性。
- **部署**:一般 CD 即可,不需手動清 Redis(§5)。

## 已知限制

- **`StringRedisTemplate` 每次呼叫新開 TCP 連線**(§6):扣庫存、token 校驗、預熱等路徑都受影響,本 ADR 只讓限流繞開,未修。
- **Redis Cluster 不相容**:合併腳本碰的 key 無法落在同一 slot(§3)。現行單一 Redis 無此問題。
- **8.5 萬次/秒是這支腳本獨佔 Redis 時的數字**:正式 Redis 同時跑扣庫存、token 校驗,實際份額較低,未量。
- **多 backend 實例各自一條連線時的表現未量**(bench 是單一 JVM、單一連線)。
- 部署切換時限流狀態重置一次(§5)。
