# ADR 0008:CD 上線與 k6 壓測(M7)— 部署拓樸、Trivy 取捨、壓測長尾延遲根因、觀測性擴充

日期:2026-08-17|狀態:已採納(M7 完成)

## 背景

M7 把系統部署上線(OCI Ampere A1,4C/24G,ARM64)並以 k6 壓測驗收。設計文件第 12 節為部署權威規格。本里程碑分兩段:子項 1–5(CD 管線,已於 2026-07-18 上線 `https://tixco.kozow.com`)與子項 6–7(k6 壓測、長尾延遲根因排查與收尾)。壓測階段挖出的長尾延遲根因(§10)是本里程碑最重要的架構發現,連帶修好一個真實的 consumer 卡死 bug(§12)。多處落地細節需就地決策,逐項記錄於下。

**範圍縮減(使用者決策)**:設計文件第 12 節第 5 步「部署結果推 Telegram 通知」略過,比照 ADR 0007 §5 的被動觀察原則,部署成敗看 GitHub Actions 頁面即可。

## 1. 部署拓樸:單機組裝

- **決策**:`docker-compose.prod.yml` 在 OCI 單一實例上組裝全部 11 個服務(Caddy、frontend、backend、postgres、redis、rabbitmq、prometheus、grafana + 3 個 exporter),不含 alertmanager(ADR 0007 §5 已定案)。
- **理由**:MVP 規模單機成本最低、部署最簡單,`WORKER_ID` 固定 0 的 Snowflake 設計本就假設單機(見 ADR 0001);多實例是保留的擴充點,非本階段需求。
- **取捨**:單點故障、無法水平擴展,發生問題時全服務一起受影響;可接受,MVP 階段追求快速上線與可觀測性優先於高可用。

## 2. 主機作業系統:Oracle Linux(非 Ubuntu)

- **決策**:OCI Ampere A1 執行個體用 Oracle Linux 9.7,`setup-server.sh` 同時支援 `dnf`/`apt` 與 `firewalld`/`iptables` 兩種家族以防未來換機型。
- **理由**:OCI 主控台建立 Always Free Ampere A1 執行個體時預設提供 Oracle Linux 映像,直接採用;非深思熟慮的技術偏好,純屬可用性最高的預設選項。
- **取捨**:`firewalld` 與 `iptables` 混用會互相打架、規則不生效——`setup-server.sh` 第一版在 OL9 上踩過這個坑,現版本偵測到 `firewalld` 運行中就不動 `iptables`,兩者互斥執行,不並用。

## 3. Dockerfile:多階段建置、非 root、Trivy 清理

- **決策**:backend/frontend 皆多階段建置,執行階段非 root(backend uid 1001、frontend 用 `nginxinc/nginx-unprivileged:1.27-alpine`,uid 101)。額外兩處為滿足 Trivy 掃描新增的清理動作:
  1. backend 移除基底映像內建、用不到的 Canonical Pebble 服務管理器(`/usr/bin/pebble`)——較舊 Go 編譯,帶有已修補但 `ignore-unfixed` 仍會擋的 `golang.org/x/net`/stdlib HIGH CVE,我們的 ENTRYPOINT 是 `java -jar` 不經過它,直接刪除從源頭消除。
  2. frontend 執行 `apk upgrade --no-cache` patch 掉 Alpine 基底映像的已知 CVE,因 `apk` 需要 root 權限,執行前後各切一次 `USER root`/`USER nginx` 維持容器內非 root 執行的安全規範(CLAUDE.md、設計文件第 10.6 節)。
- **理由**:CLAUDE.md 安全規範要求非 root 執行;Trivy 是 CD 管線的硬性關卡(HIGH/CRITICAL 即失敗),兩個清理動作都是為了讓已存在但用不到的漏洞不擋部署。
- **取捨**:`rm -f /usr/bin/pebble` 若基底映像未來移除該檔案則為 no-op,不影響冪等性;`apk upgrade` 每次建置都可能拉到不同的修補版本,建置結果非完全可重現,但換得漏洞持續修補。

## 4. Trivy 掃描做法

- **決策**:用 `aquasec/trivy:0.65.0` **Docker 映像**執行掃描(非 `aquasecurity/trivy-action`),`--scanners vuln`(關閉 secret 掃描)、`--ignore-unfixed`、`--severity HIGH,CRITICAL`、`--platform linux/arm64`(runner 是 amd64,不指定會找不到 arm64 子映像)。
- **理由**:`trivy-action` 以 `install.sh` 下載執行檔,在 GitHub Actions runner 上常因下載/rate limit 失敗(首次部署即踩到);pin 版本的 Docker 映像法穩定、且與本機驗證行為一致。
- **取捨**:`ignore-unfixed` 只擋「有修補可用」的漏洞,無官方修補的 CVE 擋了也無從修,故略過;關閉 secret 掃描換取掃描速度,secret 洩漏由「`.env` 進 `.gitignore` + GitHub Secrets 唯寫」這條路線把關,不依賴 Trivy。

## 5. Caddy 的 XFF 信任模型(取代 ADR 0004 §4)

- **決策**:`Caddyfile` **不**寫 `header_up X-Forwarded-For {remote_host}` 覆寫,移除 ADR 0004 §4 原本的建議寫法。
- **理由**:實測(送偽造 `X-Forwarded-For: 1.2.3.4`,觀察 backend 實收值)證實 Caddy 2.7 起採 `trusted_proxies` 信任模型,預設不信任任何上游,一律丟棄客戶端送來的 XFF 並改寫為真實連線來源——有無 `header_up` 這行,backend 收到的都是真實來源 IP,該指令是多餘的,Caddy 本身也會發出 "Unnecessary header_up" 警告。
- **取捨**:安全性依賴「Caddy 預設不信任任何上游」這個前提;若日後在 Caddy 前面再加一層 CDN/LB(如 Cloudflare)或設定 `trusted_proxies`,真實 client IP 的來源會改變,必須重新檢視 `ClientRequestInfo` 的取值邏輯,否則限流可能失效(全部流量被視為同一 IP)。**本節取代 ADR 0004 §4 的建議寫法**,原節理由(XFF 可偽造、限流需以真實 IP 為準)依然成立,只是實作手段不同。

## 6. 祕密管理與 CD 觸發方式

- **決策**:所有 prod 祕密經 GitHub Secrets 注入,CD 部署時 `printf` 逐行寫入主機 `/opt/seckill/.env`(權限 600),不進 log、不進 repo。CD 由 `workflow_run`(CI 於 main 成功後自動觸發)+ `workflow_dispatch`(手動重跑)雙軌驅動,`concurrency` group 鎖住同時只跑一次部署。
- **理由**:GitHub Secrets 唯寫(設定後連自己都無法從網頁讀回原值),是這條路線的安全基礎;`workflow_dispatch` 供補改 secret 後不想等 CI 重跑就能重新部署的場景(本次壓測排查過程中用來重建 admin 種子帳號密碼)。
- **取捨**:GitHub Secrets 唯寫也意味著遺失/外洩後只能靠應用層(如 admin 帳號)的重置流程處理,查密碼要 SSH 進主機讀 `/opt/seckill/.env` 明文,不能從 GitHub 網頁確認。

## 7. 網域選擇插曲

- **決策**:改用 Dynu 免費子網域 `tixco.kozow.com`,放棄原訂的 `tixgo.com`。
- **理由**:`tixgo.com` 是別人已持有、Afternic 掛售的 premium `.com`;免費 DDNS 服務給不了 `.com` 頂級域,只給自家子網域。
- **取捨**:子網域不如自有頂級域專業,但免費、立即可用,MVP 階段足夠;Caddy 對此網域自動簽發 Let's Encrypt 憑證與 HTTP/3 皆正常運作。

## 8. k6 壓測情境設計

- **決策**:兩個情境覆蓋不同壓力型態——情境 A「開賣瞬間」用 `ramping-vus`(30 秒 ramp 到 2000 VU + 持續 2 分鐘),情境 B「持續高壓」用 `constant-vus`(1000 VU 恆定 10 分鐘,70% 搶購 + 20% 查詳情 + 10% 輪詢)。帳號池用 `SCENARIO_A_USER_OFFSET`/`SCENARIO_B_USER_OFFSET` 分段(0–1999 / 2000–4999),避免兩情境互相污染。
- **理由**:單一情境無法同時驗證「瞬間爆量」與「持續壓力下系統會不會累積劣化」兩種真實場景;分段帳號池讓兩情境的對帳結果乾淨可分辨。
- **取捨**:情境 B 每個 VU 全程固定綁定一個帳號(「每人限購一張」業務規則所致),**成功購買數的天花板是 VU 數、不是庫存數**——這個限制在後續要拉高流量找下游承載上限時,曾誤導了一次測試設計(調庫存無效,需同步調 VU 數),已寫進 `load-test/long-tail-latency-investigation.md` 供下次壓測參考。

## 9. k6 腳本健壯性:safeJson

- **決策**:`load-test/lib/config.js` 新增 `safeJson()`,所有腳本的 `res.json()` 呼叫全面替換。
- **理由**:大規模壓測下偶發連線層級失敗(connection refused/timeout)時,k6 回應物件的 `body` 是 `null`,直接呼叫 `res.json()` 會拋例外把整個迭代中斷,而非像一般錯誤回應那樣回傳可判斷的物件,導致大量迭代因單一連線問題而整批失敗、統計失真。
- **取捨**:多一層防禦性判斷,換取壓測結果在部分連線失敗時仍可信、可分析。

## 10. 壓測長尾延遲根因:Redis 限流 key 熱點排隊(本里程碑核心發現)

- **現象**:情境 B(1000 VU 恆定 10 分鐘)下,`/api/v1/seckill/purchase` 的 p99 會飆到 8–30 秒(少數請求 max 17–60 秒),穩態僅個位數毫秒,每次壓測穩定重現;業務正確性不受影響(零超賣、零重複購買,每次對帳皆驗證通過)。
- **決策**:認定根因為 `seckill:rl:global`(全站唯一共用的限流 key)在 Redis 單執行緒佇列裡因熱 key 爭用而排隊,不是 DB/MQ/連線池/JIT 暖機/virtual thread pinning(逐一測過並排除,見 `load-test/long-tail-latency-investigation.md`)。
- **理由(兩階段坐實,由弱到強)**:
  1. 幫 `RateLimiterService` 四個 `try*` 方法加 Micrometer Timer 量測端到端耗時(含排隊等待),`global` 層 p99 時序幾乎逐點貼著 HTTP p99 走,`user`/`token_user` 兩層(key 按 userId 分散)全程正常。
  2. 加 dev-only 消融開關讓限流檢查整段跳過、直接 `return true`(見 §11),繞過限流排隊後 p99 從 8–30 秒直接掉到 3ms 量級,異常實質消失——證明因果關係,不只是相關。
- **取捨**:`seckill:rl:global` 是設計上無法規避的全站唯一瓶頸(所有搶購請求都要過這一關)。候選修復方向(CAS 兩次往返改單一 Lua 原子操作、sharded counter 拆分子 key、評估 Bucket4j 高併發替代設定)皆已列入 `load-test/long-tail-latency-investigation.md`,**本里程碑只坐實根因,未動手修復限流器本身的演算法**,修復與下游真實承載上限測試留待後續。

## 11. 消融測試開關(dev-only)

- **決策**:`RateLimiterService` 新增 `bypassEnabled` 欄位,`tryGlobal`/`tryUser`/`tryIp`/`tryTokenUser` 開頭皆加 `if (bypassEnabled) return true;`;`application.yml` 僅在 **dev profile** 區塊新增 `seckill.ratelimit.bypass-enabled: ${SECKILL_RL_BYPASS:false}`。
- **理由**:要坐實 §10 的根因,需要一個能讓下游系統直接暴露在真實流量下、不被限流器自身排隊干擾的乾淨對照組;不是調高 `global-capacity`(已證實容量調再高也不會減少 Redis CAS 呼叫次數,對此問題無效)。
- **取捨**:這個 key 只存在於 `application.yml` 的 dev profile 區塊,prod profile 沒有對應設定,即使誤設 `SECKILL_RL_BYPASS` 環境變數也不會在 prod 生效,預設值 `false` 不影響正常環境行為。開關程式碼予以保留(未刪除),因後續找下游承載上限測試還會用到,且本身無副作用。

## 12. OrderCreateListener 冪等分支卡死 bug(壓測意外挖出的真實缺陷)

- **決策**:`onOrderCreate()` 的 `catch (DuplicateKeyException e)` 冪等分支(補寫 `resultCache.writeSuccess`)改包一層 try-catch,失敗時導去既有的 `handleUnexpected()` 走統一的 `x-retry-count` 重試/DLQ 保護機制,不再讓例外直接從 catch 區塊冒泡逃出。
- **理由**:壓測時因客戶端 TCP 埠耗盡連帶讓 backend 對 Redis 的連線暫時失敗,原本的冪等分支若 `writeSuccess` 失敗會完全繞過 `handleUnexpected` 的重試上限與死信保護,導致訊息卡在佇列裡出不去也死不了——實測 `seckill.order.queue` 卡了 2465 筆訊息、consumer 靜止 18 分鐘以上未自行恢復,`seckill.order.dlq` 卻是 0(證實沒有死信,是真的卡死)。業務資料本身沒有遺失(`orderCreateService.createOrder(message)` 是這個方法的第一步,在 `writeSuccess` 之前已執行,訂單早已落庫)。
- **取捨**:此缺陷只在「Redis 暫時不可用」這種故障情境下才會觸發,不是 §10 長尾延遲的根因(兩者為壓測過程中各自獨立的發現);修復後用真實卡住的資料驗證過(重啟後佇列歸零、對帳恢復 `consistent:true`),已於 CI 綠燈後上線正式站。

## 13. 個人開發工具與可觀測性 GUI 存取

- **決策**:`docker-compose.tools.yml`(RedisInsight)與 `docker-compose.dev.yml`/`docker-compose.prod.yml`(應用程式依賴)、既有的 Prometheus/Grafana(專案審查過的可觀測性設定,ADR 0007)分開放;`docker-compose.prod.yml` 追加 Postgres(5432)與 RabbitMQ management(15672)的 **loopback-only** port,比照既有的 Prometheus/Grafana 模式,經 SSH tunnel 存取。
- **理由**:Postgres/Redis/RabbitMQ 是 backend 硬性依賴,Prometheus/Grafana 是設計文件明確規劃、掛了審查過 dashboard/alert-rules 的產品功能,兩者都不適合跟「純粹圖個方便的第三方 GUI 工具」混在同一份定義檔——RedisInsight 沒有任何專案專屬設定,拿掉它不會遺失任何審查過的產出物,理當可以自由替換,獨立於前兩者的生命週期。開 loopback port 而非公網,只綁 `127.0.0.1`,需先 SSH 進主機才碰得到,不擴大攻擊面。
- **取捨**:CD 部署腳本需額外一步動態查詢 `docker-compose.prod.yml` 實際的 compose 網路名稱(project name 為 `seckill-prod`,非目錄名 `seckill` 推得,原因不明,已用 container label 實測確認)才能讓 `docker-compose.tools.yml` 正確接上同一網路,比寫死字串多一道查詢步驟,換取部署細節變動時不會無聲斷掉。

## 驗收與已知限制

**驗收**:CI/CD 全綠,正式站 `https://tixco.kozow.com` 對外 HTTPS 200、合法 Let's Encrypt 憑證、HTTP/3 啟用;情境 A/B 壓測零超賣零重複購買(每輪皆對帳驗證);長尾延遲根因已用 Timer 量測 + 消融測試雙重坐實(§10);`OrderCreateListener` 修復已用真實卡住的資料驗證(§12)。

**已知限制**:
- **下游真實承載上限尚未測出**:HANDOFF.md 規劃的步驟 2–4(繞過限流找 DB/MQ/建單真實承載上限、單一 Redis 節點 CAS 上限、合併算 sharded counter 分片數)因本機測試拓樸撞上 Windows 客戶端 TCP 埠耗盡而數據作廢,且使用者決定改到 OCI 正式站上測,**本里程碑尚未執行**,留待後續 session。
- **限流器演算法本身未修復**:§10 只坐實根因,`seckill:rl:global` 的 CAS 兩次往返/sharded counter 等候選修復方向皆未實作。
- **設計文件第 11 節的告警閾值(3000 QPS、p99 500ms、消費併發等)仍是初值,未依本次壓測結果校準**(ADR 0007 §5 已標記待辦,本里程碑因下游承載測試未完成,無法回頭校準)。
- **壓測記錄分三份**:`docs/load-test-report.md`(run1–4,完整驗收報告)、`load-test/long-tail-latency-investigation.md`(run5–11,根因排查完整過程與原始數據)、`HANDOFF.md`(僅待辦事項,不放歷史記錄)——三者需搭配閱讀才是完整脈絡。

**建議 review 重點**:Caddy XFF 信任模型是否需要在導入 CDN/LB 時重新檢視(§5)、消融開關的 dev-only 邊界是否足夠安全(§11)、`OrderCreateListener` 修復是否需要為其他消費者的類似冪等分支做同樣的健壯性檢查(§12)、`docker-compose.tools.yml` 這種「個人工具獨立分離」的慣例是否要延伸到其他個人偏好工具(§13)。
