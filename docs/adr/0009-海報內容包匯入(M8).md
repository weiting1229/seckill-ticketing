# ADR 0009:海報內容包匯入(M8)— 藝人表、批次匯入端點與上傳安全設計

日期:2026-09-07|狀態:已採納(M8 後端段完成)

## 背景

實作計畫:[`docs/plans/2026-08-18-poster-dynamic-management.md`](../plans/2026-08-18-poster-dynamic-management.md),含該檔 2026-09-06 的 S1–S9 契約修訂。

海報由 poster-forge 專案(`C:/Users/USER/Documents/poster-forge`)離線產出:模型生無文字底圖 → 程式合成標準字 → 人工挑圖核可 → `pnpm pack:content` 匯出成 `curated/content-pack.json` + `curated/posters/`(46 張 1200×675 WebP,合計 2.81 MB)。本里程碑做的是**把那份成品搬進 seckill 的通道**,以及它落地後的資料表。

**本里程碑的範圍**(使用者 2026-09-07 拍板,**當天稍後擴充**):

- 第一段:後端 API + 圖片落地 + 測試(§1–§13)
- 第二段:計畫 §8 Task 4 的靜態路由、主機目錄與備份(§14–§17)—— 圖片對外提供得出來
- 第三段:計畫 §8 Task 7 的前端(§18–§20)—— **首頁卡片顯示真海報**

**仍不含**:`AdminArtistsView` 與其 router(S7 判定不做,內容的唯一可寫入口是匯入)、seeder。

seeder(`DemoContentPool` / `DemoEventSeeder`,計畫 `2026-08-17-demo-event-seeder.md`)**仍未實作**,`artists` 表目前沒有任何消費端在讀。

## 1. Flyway 版號用 V4,不是計畫寫的 V6

- **決策**:`V4__create_artists.sql`。計畫 §5 寫的是「承接 seeder 計畫的 V4 / V5,本計畫從 V6 起算」。
- **理由**:實查 seeder 計畫**完全未實作**,V4 / V5 沒有佔號,倉庫裡最大的是 `V3__add_event_featured_fields.sql`。若這裡跳號用 V6,等日後真的補上 seeder 的 V4 時,Flyway 預設 `outOfOrder=false` 會判定「已套用的版本之前出現新 migration」而**讓 backend 啟動失敗**——而那是部署當下才炸,不是開發時。
- **取捨**:seeder 計畫的版號規劃作廢,那份計畫日後要從當時的最大號往後接。這比讓一次部署炸掉划算。

## 2. 藝人表的中英名:`name_en` 必填、`name_zh` 可為 NULL(推翻計畫 S3)

- **決策**:`name_en VARCHAR(100) NOT NULL UNIQUE`;`name_zh VARCHAR(100)` 可為 NULL,唯一性走**部分唯一索引** `WHERE name_zh IS NOT NULL`,並以 CHECK 擋空字串。顯示名由應用層推導成 `name_zh || name_en`,**不存成欄位**。
- **理由**:計畫 §5 的 S3 標註寫「新增 `name_en`,可為 NULL:不是每個團都有英文名」。**實測內容包 46 筆,結論正好相反**:`nameEn` 46/46 都有且互不重複,`nameZh` **有 23 筆是空的**。照抄原本的 `name VARCHAR(100) NOT NULL UNIQUE` 有兩種死法,而且都不是好看的死法——空字串寫進去會在第 2 個沒有中文名的藝人撞唯一鍵、整批匯入失敗;若改成允許 NULL 但保留欄位層 UNIQUE,PostgreSQL 雖允許多個 NULL,空字串卻仍會互撞,所以還必須把空字串正規化成 NULL 才成立。
- **取捨**:顯示名每次查詢都要推導,不能直接在 SQL 上對它做索引或搜尋;目前沒有「依顯示名搜尋藝人」的需求。推導規則與 poster-forge `src/identity/artists.ts` 的 `name = nameZh || nameEn` **必須一致**——兩邊若各自推導出不同的名字,前端的 `title.includes(artist)` 比對會安靜地全數落空,退回生成式 SVG 而不報錯。

## 3. 海報存獨立子表 `artist_posters`,不用 `posters JSONB`(結案計畫 §11 待決 #7)

- **決策**:獨立子表,`file_name VARCHAR(200) NOT NULL UNIQUE` 為匯入冪等鍵,附 `archetype` / `theme_index` / `seed` / `sort_order`。
- **理由**:冪等匯入需要一個**唯一鍵**才能判斷「這張海報是新的還是既有的」,而 JSONB 陣列給不了唯一約束。用 JSONB 的話,檔名重複只會在覆蓋掉舊資料的那一刻被發現,而那一步不會報錯。子表另有一個好處:同一個檔名換了所屬藝人(poster-forge 改過 slug 推導)時,`UPDATE ... SET artist_id` 一行就搬過去了。
- **取捨**:多一個 mapper 與一次 `IN (...)` 查詢;讀一個藝人不再是單列。海報 URL 一旦發出去就有人存了,所以這個形狀是**現在就必須定**的——欄位改成陣列要搬資料,而搬資料時 URL 已經在對方的資料庫裡。

## 4. 匯入走單一批次端點,不用逐張上傳(結案計畫 §11 待決 #6)

- **決策**:`POST /api/v1/admin/artists/import`,一個 multipart 請求帶 `manifest`(JSON)+ N 個 `files`(WebP),DB 寫入落在同一個交易。計畫 §6 原本規劃的 `POST /admin/artists/{id}/poster`(一次一張、要先有 artist id)**不實作**。
- **理由**:逐張的形狀匯入這一輪的東西,是先打 46 次 CRUD 建藝人、再打 46 次上傳。中途任何一步失敗就停在半套,而「半套」在這裡的樣子是**首頁部分卡片有圖、部分沒有**——沒有任何一步會報錯,只有人眼看得出來。
- **取捨**:單一請求會變大(實測 2.88 MB,`max-request-size` 設 32MB 留餘裕);內容包成長到數百張時要重新評估是否分批。這個上限只有 ADMIN 打得到。

## 5. 檔案與 DB 的寫入順序:先落檔、後寫 DB

- **決策**:校驗全部跑完 → 寫入所有海報檔 → DB 交易。檔案系統不參與交易,失敗時**留下孤兒檔而不回滾**。
- **理由**:檔案系統不能加入交易,所以兩種失敗必有其一。先落檔後寫 DB,DB 失敗時留下的是**沒有任何一列引用的孤兒檔**:無害、可由孤兒清單端點列出後人工清掉。反過來先寫 DB 後落檔,落檔失敗時 DB 指向**不存在的檔案**:前台整片破圖,而破圖不會出現在任何日誌裡。這與計畫 §4.4 對單張替換的規定同源。
- **取捨**:目錄會累積孤兒檔,需要人工定期清(計畫 §10 已列為已知限制)。另外每個檔案是「寫暫存檔 → 原子改名蓋上去」而不是直接對正式檔名寫入:直接寫的話,寫到一半失敗會留下**半張圖覆蓋掉原本正常的那張**,而半張 WebP 在瀏覽器上是破圖不是錯誤。

## 6. 匯入 manifest 是精簡版,不收原始的 content-pack.json

- **決策**:poster-forge 的 `pnpm publish:seckill` 送的是去掉 `posters[].layout` 的精簡 manifest;端點的 `ObjectMapper` **開啟 `FAIL_ON_UNKNOWN_PROPERTIES`**,多送欄位當場回 1400。
- **理由**:`layout` 是烘焙用的排版座標、字型授權與選版理由,序列化後佔整份 106 KB 的 **90%**(去掉只剩 10.7 KB),而字已經烤進點陣圖,這一端不會有任何一行程式讀它。真正的理由不是省頻寬而是**契約的邊界**:收進來的欄位,日後有人會以為是契約的一部分而不敢動。
- **取捨**:poster-forge 多維護一層 `manifest.ts` 轉換。`FAIL_ON_UNKNOWN_PROPERTIES` 也意味著內容包日後新增欄位時,兩邊必須同時改——這是刻意的,寧可當場退回也不要安靜丟掉。

## 7. 刪除 `title_style` 欄位(採納計畫 S6)

- **決策**:表裡**不建** `title_style`,連帶不做前端 CSS 疊字 fallback。
- **理由**:計畫 §4.3 的 2026-08-22 標註把 `title_style` 定位成「藝人有名字但還沒上傳海報」時的 fallback,並要求前端沿用 poster-forge `src/compose/template.ts` 的 `TitleStyle`。但那個檔案在 poster-forge 的 layout 架構計畫 §15 已標記**待刪**,取代它的產出是烤好的點陣圖,沒有任何可以給前端套用的 CSS 參數;照抄的下場是前端疊的字跟海報上的字是兩套視覺,而不會有任何錯誤。**同時 fallback 情境本身也不存在了**:內容包的匯出跳過沒有核可海報的藝人,表裡不會出現「有藝人但沒有海報」的列。
- **取捨**:**這個決定依賴一個不變量**——任何寫進 `artists` 表的藝人都帶著至少一張海報。匯入端點以 `posters` 非空陣列(`@NotEmpty`)強制它。哪天改成「先建藝人、之後再補圖」,這個前提就破了,破的樣子是首頁出現沒有圖的卡片。

## 8. admin 不提供藝人的建立 / 改名 / 刪除(採納計畫 S7)

- **決策**:`AdminArtistController` 只有匯入、唯讀檢視、`enabled` 切換與孤兒檔清單。計畫 §6 的 `POST` / `PUT` / `DELETE` **不實作**;§8 Task 3 的種子 bootstrap 一併刪除(S8)。
- **理由**:藝人的名字、tier、巡演主題全部在 poster-forge 編寫並隨內容包進來。後台再開一套增刪改,等於同一份資料有兩個可寫入口——兩邊不一致時沒有任何一步會報錯,只會在下一次匯入被安靜覆蓋掉。種子 bootstrap 同理:空表啟動時先塞一批硬編碼藝人再被匯入覆蓋,中間那段時間前端顯示的是不存在的團。
- **取捨**:要改一個團名必須回 poster-forge 改、重跑匯出、重新匯入。這正是想要的方向:一份資料一個來源。`enabled` 是唯一的例外,它是營運開關不是內容編輯——所以**匯入不覆寫既有藝人的 `enabled`**,否則管理員停用過的藝人會在下一次匯入自己活過來。

## 9. 上傳安全:不引入影像函式庫,自己讀 WebP 檔頭

- **決策**:`WebpImage` 手寫解析 RIFF 容器與三種 chunk(`VP8 ` / `VP8L` / `VP8X`),只讀畫布尺寸,**一個像素都不解碼**。不加 TwelveMonkeys 或 webp-imageio。
- **理由**:Java 標準 `ImageIO` 不支援 WebP,而計畫 §4.4 要求驗尺寸(擋解壓縮炸彈與異常尺寸)。CLAUDE.md 要求新依賴先說明用途與替代方案——這裡需要的只是「前 30 個位元組是不是一張合法 WebP、畫布多大」,**解碼反而把解壓縮炸彈的攻擊面搬進來**,而擋炸彈正是讀尺寸的目的。三種 chunk 都支援是因為 poster-forge 目前 46 張全是 VP8,但編碼參數改一次就會變;只認 VP8 的失敗樣子是「換了壓縮設定之後整批被拒,而錯誤訊息說格式不合法」。
- **取捨**:多一份要維護的格式解析。解析公式在寫 Java 之前先以實際 46 張驗證過(RIFF 宣告長度全部精確吻合、尺寸全部解出 1200×675),另有 7 個單元測試涵蓋三種 chunk 與四種拒絕情境。

## 10. 上傳檔名的信任模型:當查表的鍵,不當路徑

- **決策**:三道關卡。(1) `ImportRequestReader` 剝掉 part 檔名的任何目錄成分;(2) 剝完的名字**必須出現在 manifest 裡**,而 manifest 的每個檔名已先過白名單 `^[a-z0-9][a-z0-9_-]*\.webp$`;(3) `PosterStorage.resolve` 實際落檔時再斷言解析後的父目錄就是根目錄。DB 亦有同一份規則的 CHECK。
- **理由**:計畫 §4.4 要求「檔名完全由伺服器決定」。這裡的形狀不同——批次匯入必須靠檔名把 part 對應回 manifest 條目,所以檔名不能丟掉。改成「檔名只當查表的鍵」在安全性上等價:送 `../../evil.webp` 會在第二道因為不在 manifest 而讓**整批**被拒。第三道是防白名單日後被放寬(例如想允許子目錄)那天,路徑穿越安靜地成立。
- **取捨**:檔名的唯一性責任落在 poster-forge(`<slug>__<版式>.webp`)。它同時是 DB 的唯一鍵,所以重複會被擋下而不是安靜覆蓋。

## 11. `tour_themes` 用 JSONB,以 `Types.OTHER` 而非 `PGobject` 寫入

- **決策**:`tour_themes JSONB NOT NULL DEFAULT '[]'`,MyBatis 自訂 `TourThemeListTypeHandler`,寫入端用 `ps.setObject(i, json, Types.OTHER)`。
- **理由**:主題是整包讀寫、從不依內容查詢的資料,JSONB 合適(計畫 S2)。寫入端若用 `setString`,PostgreSQL 會以 `column "tour_themes" is of type jsonb but expression is of type character varying` 拒絕——那是啟動後第一次匯入才會炸的執行期錯誤,單元測試看不到。常見解法是 `org.postgresql.util.PGobject`,但 pom 裡 postgresql 驅動是 `runtime` scope(應用程式碼不該編譯依賴特定驅動),import 它等於把 scope 提升成 compile。`Types.OTHER` 讓驅動送出未指定型別的參數,由伺服器依目標欄位推斷,效果相同且是 JDBC 標準寫法。
- **取捨**:JSONB 沒有型別檢查,欄位打錯不會在 DB 層被擋(計畫 §10 已列為已知限制)。⚠ **欄位必須允許空陣列**:實測 46 個藝人有 19 個沒有巡演主題,對應的 `artist_posters.theme_index` 為 NULL——不可用 0 或 -1 代替,兩者都指向不存在的一筆,而消費端取到 `undefined` 不會報錯。

## 12. 錯誤碼新增 5xxx 分段(擴充設計文件第 9 節)

- **決策**:`5001` 藝人不存在、`5002` 名稱重複、`5003` slug 重複、`5004` 圖片格式不合法、`5005` 圖片尺寸不合法、`5006` manifest 與上傳檔案不一致、`5007` 檔案寫入失敗。同時為 `MaxUploadSizeExceededException` 與 `MissingServletRequestPartException` 加全域處理。
- **理由**:設計文件第 9 節只定義到 4xxx(訂單),藝人管理是新領域。`5006` 是計畫 §4.7 沒有預見的:批次匯入才有「manifest 與檔案集合對不上」這種錯。兩個 multipart 例外若不接,會落到 catch-all 變成 `9999 系統錯誤`——而那其實是參數問題,訊息裡連「檔案太大」四個字都沒有。
- **取捨**:設計文件第 9 節需要同步擴充。

## 13. 校驗全部在寫入之前,且每一條擋的都是「不會報錯的錯」

- **決策**:`ArtistImportService` 在寫任何檔案之前擋下:內容包版本不符、manifest 內部 slug/團名/檔名重複、`themeIndex` 超出該藝人的主題數、manifest 與上傳檔案**雙向**不一致、非 WebP、尺寸越界、團名撞到別的 slug 已佔用的名字。
- **理由**:共同點是**不擋的話不會報錯,只會發佈到錯的東西**。`themeIndex` 越界前端只會少渲染一段文字;檔案集合的單向檢查會漏掉「上傳了但 manifest 沒宣告」——那張圖使用者以為已經發佈了,實際上誰也不引用;團名撞唯一鍵若不先擋,使用者拿到的是 `9999` 而訊息裡沒有任何一個團名。
- **取捨**:重複了一部分 poster-forge 匯出時已經做過的檢查。這是刻意的:匯入端不能假設上游一定跑過檢查,而這些檢查全部是純比對,成本可忽略。反過來,poster-forge 的客戶端**不**重複驗 WebP magic bytes 與尺寸——兩邊各寫一份規則遲早會有一邊改了另一邊沒改,而不一致的樣子是「本機說可以、送過去被拒」。

## 14. 靜態路由塞在 catch-all 之前,且**不可**標 `immutable`

- **決策**:Caddyfile 在 `handle /api/*` 之後、catch-all `handle` 之前插入 `handle_path /posters/* { root * /srv/posters; file_server; header Cache-Control "public, max-age=3600" }`。不開 `browse`。
- **理由(位置)**:`handle` 區塊互斥且**依檔案順序**評估,與 `/actuator` 是同一個坑。放到 catch-all 之後會被前端 SPA fallback 吃掉,而 SPA fallback 回的是 **200 + index.html** —— `<img>` 會拿到一份 HTML 當圖片解碼失敗。**破的樣子是「圖不出來但 network 面板全綠」**,所以驗收必須看 `Content-Type` 而不是只看狀態碼。
- **理由(快取)**:第一版寫的是 `max-age=31536000, immutable`,**當場推翻**。檔名 `<slug>__<版式>.webp` 是**識別**不是內容雜湊:同一個藝人的同一個版式換底圖重新核可時,匯入會就地覆蓋同一個檔名——內容變了、URL 沒變。標 `immutable` 的訪客會一整年拿到舊圖,而且瀏覽器根本不會回來問,沒有任何一步報錯。改成 1 小時 + Caddy `file_server` 自動帶的 ETag / Last-Modified,實測過期後一次 304 就結束。
- **取捨**:每小時一次條件請求的成本換掉「換圖後永遠更新不了」的風險。真的要長快取,正確做法是讓 poster-forge 的檔名帶內容雜湊,那是另一個決定(URL 已經發出去了,見 §3)。

## 15. 主機目錄的屬主必須是 uid 1001,而且 `chown` 的順序會咬人

- **決策**:`setup-server.sh` 建立 `$APP_DIR/posters` 並 `chown -R 1001:1001` + `chmod 0755`,**放在既有的 `chown -R "$APP_USER"` 之後**。compose 讓 caddy 唯讀掛載、backend 可寫掛載同一個主機目錄。
- **理由**:bind mount 沿用主機的屬主與權限,而 backend 容器以 `backend/Dockerfile` 建立的 `app`(uid 1001)執行。屬主不對的話**啟動不會失敗**——目錄已存在,Java 的 `createDirectories` 是 no-op——而是等到有人真的匯入海報時才 permission denied,失敗點離原因很遠。順序同理:若把 posters 的建立放在 `chown -R "$APP_USER" "$APP_DIR"` 之前,那個遞迴 chown 會把屬主改回去,而腳本會成功結束。
- **取捨**:`setup-server.sh` 從此與 Dockerfile 的 uid 耦合,**改 Dockerfile 的 uid 必須同步改這裡**(兩邊都留了警告註解)。腳本直接寫數字 uid 而非名稱,因為主機上不存在 uid 1001 的使用者,`chown app` 會失敗。caddy 那邊唯讀掛載所以不受影響:寫入是 backend 的事,掛成可寫的話一個 Caddy 設定錯誤就能改到圖檔。

## 16. 備份擴充是先決條件,不是加分項

- **決策**:`backup-db.sh` 在 pg_dump 之後加一段 `tar czf posters-<timestamp>.tar.gz`,同一個目錄、同一個保留天數、同一條 cron。海報那段失敗**不 `exit`**,只寫 stderr。
- **理由**:海報從 M8 起刻意脫離 git(圖片不進 repo),所以在這裡被打包之前,它是全系統唯一一份**沒有任何保護**的資料——主機重建或誤刪就沒了,而重做要回 poster-forge 重跑整條生圖 / 挑圖 / 核可流程。不 `exit` 是因為 DB dump 已經成功了,不該讓整條 cron 看起來全滅。
- **取捨**:粒度是每日一次,當天匯入後誤刪救不回來(計畫 §10 已列)。空目錄也照打包:「沒有備份檔」與「備份了但目錄是空的」在事後排查時是兩件不同的事。

## 17. dev 的落點改指向 `frontend/public/posters`

- **決策**:dev profile 的 `seckill.posters.dir` = `../frontend/public/posters`(相對於 `backend/`,即 runbook 的 dev 啟動目錄);該路徑加進 `frontend/.gitignore`。共用預設仍是 `./data/posters`,prod 由 `SECKILL_POSTERS_DIR=/srv/posters` 覆寫。
- **理由**:計畫 §4.6 要求 dev / prod 的對外路徑都是 `/posters/<檔名>`,前端程式碼不區分環境。dev 沒有 Caddy,由 Vite 的 `publicDir` 提供——但匯入端點若仍寫進 `backend/data/posters`,**匯入會成功而前端看不到圖,且不會報錯**。
- **取捨**:相對路徑綁定啟動時的工作目錄。從 repo 根目錄啟動 backend 會讓它落在 repo 外面,症狀同樣是「匯入成功但看不到圖」——已在 `application.yml` 就地寫明,要從別處啟動就用 `SECKILL_POSTERS_DIR` 指絕對路徑。

## 18. 海報三層解析,失敗時往下掉一層而不是掉到底

- **決策**:`composables/useEventPoster.ts` 統一決定一個活動用哪張圖:`coverImageUrl` → 標題比對到的藝人海報 → `null`(呼叫端渲染 `GenerativePoster`)。載入失敗以 **URL** 為鍵記錄,不是以活動 id。
- **理由**:既有三個渲染點(列表卡、精選輪播、詳情頁 hero)各自寫了一份「有封面就用封面、壞了就用 SVG」,而且都把失敗記成「這個**活動**的封面壞了」。插進第 2 層時若沿用活動 id,第 1 層一壞就會直接跳到第 3 層——一個 404 的 `coverImageUrl` 會讓該活動**看不到本來有的藝人海報**。改記 URL 之後每一層各自降級,而且同一張藝人海報被多個活動共用時只需要壞一次。
- **取捨**:三個渲染點改成共用一個 composable,各自的 `failedUrls` 不共享(同一次進站重複試同一張壞圖最多三次)。共享要再加一層 store,不值得。

## 19. 拉丁團名比對要求詞邊界,中日韓不要

- **決策**:`utils/posterRegistry.ts` 對整串都是拉丁字母/數字的團名要求「左右不得緊鄰英數字」,其餘(中文)用純 `includes`。多個命中時取**最長**的名字,長度相同再依 slug。
- **理由**:內容包裡有 `Mint` / `Dodo` / `Mist` / `Astra` 這種短英文名。純 `includes` 的話,一個叫「Mistake Tour 2026」的活動會命中藝人 `Mist`,**掛上完全無關的海報而且不會報錯**——那條路徑上每一步都成功了,只有人眼看得出來。中文沒有詞邊界可用(「第七象限」前後本來就會直接接漢字),只能靠上游保證:poster-forge 硬規則 #3 要求團名之間子字串互斥,`validateArtists` 會擋;實測 46 個藝人共 69 個中英名字,互斥違反 0 筆。取最長是為了讓「標題同時含兩個團名」有一個與 API 回傳順序無關的答案。
- **取捨**:比對仍是啟發式的,不是身分關聯——這是**降級路徑**。計畫 S5 定案由 seeder 建活動時直接寫 `coverImageUrl`,那條做完之後這裡就只服務手動建立的活動。⚠ 但 `CreateEventRequest` / `UpdateEventRequest` 的 `coverImageUrl` 目前是 `@Pattern("^(https?://.+)?$")`,**存不了 `/posters/x.webp` 這種同源相對路徑**;實作 seeder 前必須先放寬它,否則 S5 那條路是走不通的。

## 20. 藝人 store 失敗一律不阻塞渲染,且單一航班

- **決策**:`stores/artists.ts` 的 `ensureLoaded()` **不拋例外**,失敗時把清單設成空陣列;`api/artists.ts` 帶 `silent: true` 不彈 `ElMessage`;多個元件同時呼叫共用同一個 in-flight promise。
- **理由**:海報是裝飾,抓不到就全站退回生成式 SVG——那是一個完全可用的畫面。讓呼叫端 `await` 之後才渲染列表,等於把一個純視覺的降級變成整頁卡住;彈一個紅色錯誤訊息則是給使用者一個他無法行動的資訊,而且會讓降級看起來像故障。單一航班是因為列表頁與精選輪播在同一次進站幾乎同時掛載,不共用的話一次進站打兩次同樣的請求——**兩次都會成功,所以沒有任何一步會報錯**,只是白打一次。實測單次頁面載入 1 次請求。
- **取捨**:只在啟動時抓一次,後台匯入新內容包之後已開著的分頁要重整才看得到(計畫 §10 已列)。demo 場景可接受,不值得為它加輪詢。

## 已知限制

- **prod 尚未實際部署驗證**:§14–§17 的改動已在本機以真的 Caddy 容器 + 真的 46 張圖驗過路由、Content-Type、404 行為與 304 重新驗證,但**沒有跑過一次真正的 CD 部署**。計畫 §9 提醒部署順序有依賴:`setup-server.sh` 的 posters 目錄必須先存在,backend 才寫得下去——而該腳本在主機上只跑過一次(M7),**這次的新段落必須重跑**,否則第一次匯入會 permission denied。
- **標題比對是啟發式的,不是身分關聯**:活動與藝人之間沒有外鍵,靠的是「標題裡有沒有出現團名」。S5 定案的正解是 seeder 建活動時直接寫 `coverImageUrl`,但那需要先放寬該欄位的 `@Pattern`(見 §19)。
- **`artists` 表仍然沒有寫入端以外的消費端**:seeder 未實作,所以沒有任何活動是「為某個藝人產生的」;現在畫面上的對應全部來自標題文字。
- **store 只在啟動時抓一次**:後台匯入新內容包後,已開著的分頁要重整才看得到。
- **圖片沒有版控與 rollback**。備份粒度是每日一次的 tar,當天匯入後誤刪救不回來。
- **快取 1 小時**:換圖後最多一小時才會全面生效(見 §14 為什麼不能標 immutable)。
- **`staleArtists` 與孤兒檔只列出不自動處理**。DB 有而內容包沒有的藝人,成因可能是核可被撤下、也可能是匯出時跳過,兩者的正確處置不同;自動刪檔在這種對照關係上,一次比對失誤就是永久資料損失。
- **公開藝人清單全量回傳、無分頁、無快取 header**(計畫 §11 待決 #4 維持不加:demo 時最容易讓人以為是沒存到)。46 筆規模沒問題。
- **`copy`(活動文案池)沒有落地**:內容包裡它一律是空陣列(poster-forge 還沒有來源),送一個永遠是空的欄位過去只會多一個問號。等文案有來源再一起加(計畫 §11 待決 #8)。
